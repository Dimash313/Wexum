# Wexum Identity: isolated OAuth transaction building block

**Prototype only.** No login service, token acceptance, organization membership, HTTP endpoint or production security assurance. Issue #34; independent of Wexum Core/VPN code and of the unmerged foundation integration.

Python 3.12+ / stdlib only. Run the local tests from the repository root:

    PYTHONPATH=apps/platform/identity/src python -m unittest discover -s apps/platform/identity/tests -v
    python -m compileall -q apps/platform/identity/src apps/platform/identity/tests

AuthorizationTransactions.begin(...) returns state, nonce, code_challenge and S256 for trusted server-side OIDC authorization initiation. The caller must provide a server-owned browser session binding and configured issuer/client/redirect. consume(...) requires the same trusted binding/configuration and matching authorization-response issuer (iss under RFC 9207), and yields server-only PKCE verifier and expected ID-token nonce once. It **does not** validate token responses. Do not create an authenticated actor from these values. Tokens, scopes, membership and sessions require independently reviewed implementations.

The store is process-local and intentionally loses outstanding attempts on restart; do not run multi-replica callback routing with this implementation. Capacity and expiry are bounded (default: 1024 global and the smaller of 4 or the global limit per browser session; both limits enforced atomically). This is not a replacement for network-edge throttling or an abuse-resistant persistent session store. Consult docs/platform/identity/THREAT_MODEL.md before integrating; requests for shared API changes go to the CTO/integrator.

`discard_pending_for_session(browser_session=...)` atomically removes outstanding login attempts for one trusted browser-session binding (e.g. during logout or session rotation). This does **not** revoke the actual browser session: the upstream session manager must separately revoke/rotate it and reject future attempts using an invalidated binding. The API only manages attempts in this one process. `AuthorizationStart` and `ExchangeContext` redact state, nonce and verifier from default object `repr`, but callers must still keep their fields and URLs out of logs.

Callback boundary (still a prototype): `parse_authorization_callback(pairs)` accepts only a bounded list/tuple of already URL/form-decoded parameter pairs, retaining duplicates. It rejects repeated fields, OAuth error responses, absent state/code/iss, oversized/malformed values and invalid RFC 9207 HTTPS issuers. Unknown unique extension fields are ignored. It returns an **untrusted** code, state and response issuer; a trusted server must still bind state/issuer/session using `AuthorizationTransactions.consume` before any token exchange. HTTP adapters MUST preserve parameter multiplicity, reject both GET/POST sources in the same callback, enforce byte/body limits before decoding, avoid logging code/state, and never derive configured client/issuer/redirect from user input. This parser does not establish identity or verify tokens. Reference: RFC 6749 (code flow) and RFC 9207 (issuer).

Composed pre-exchange boundary: `prepare_code_exchange(transactions, decoded_pairs=..., browser_session=..., issuer=..., client_id=..., redirect_uri=...)` first invokes the strict callback parser, then atomically consumes the matching pending transaction against **trusted server context**. It returns an `UnverifiedCodeExchange` with code, PKCE verifier, expected OIDC nonce and pinned issuer/client/redirect fields; secret-bearing attributes are excluded from default repr. A malformed callback does not burn a valid attempt, but a successfully prepared exchange cannot be replayed even if the subsequent token request fails. This helper performs **no actual token exchange, token signature/claim verification, session creation or authorization**. The HTTP adapter and a separately approved OIDC verification service remain required. All fields are still sensitive through direct access and must not be logged.

Raw transport boundary (no HTTP listener): `decode_callback_pairs(method=..., response_mode=..., query_string=..., body=..., content_type=...)` accepts raw **bytes** from the HTTP adapter and returns a sequence of decoded name/value pairs, preserving duplicates for the strict callback parser. `response_mode` MUST come from trusted client configuration; query mode requires GET and form_post requires POST with application/x-www-form-urlencoded (UTF-8 only). Both inputs must be passed separately, with *no framework pre-decoding or map coercion*. The decoder denies mixed transports, malformed percent-escapes, invalid UTF-8, ambiguous/body or content-type mismatches, empty/bare fields, control/non-ASCII unencoded bytes, raw fragment markers, and more than 8192 raw bytes or 32 parameters. Compose `decode_callback_pairs` → `prepare_code_exchange`; still no token verification, actual HTTP service or authorized actor. The HTTP adapter MUST independently enforce request body/header/URL limits and registered queryless redirect URIs for form_post. Only a policy-approved response mode should be selected. Strictness may reject providers outside this explicit contract and requires CTO review before integration.

Trusted web-client configuration wrapper: `ConfiguredWebOAuthClient(issuer=..., client_id=..., redirect_uri=..., response_mode=...)` is a **frozen settings object built only from audited deployment configuration**; it forbids non-HTTPS, userinfo, invalid ports, URL queries/fragments, embedded whitespace, backslash and nonregistered response modes. It deliberately accepts only HTTPS browser redirects with no static query. Native OAuth loopback/custom schemes need their own separately approved adapter rather than weakening this web boundary. Its `begin(...)` pins server issuer/client/redirect to the temporary transaction; `prepare_callback(...)` picks a trusted response mode, decodes raw GET/query or POST/form_post parameters, then atomically consumes that transaction before handing an **unverified** code+PKCE verifier to a future OIDC token adapter. The wrapper cannot prove that a syntactically valid provider is approved or that a browser-session binding is authentic; those are upstream responsibilities. Do not construct it from request parameters or use it to create an authenticated principal.
